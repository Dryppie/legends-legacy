# Loadout placement: monitor failure preservation

Current status: the outer monitor preserves its first failure through selected accounting and publication cleanup errors, attempts both publication finalizers, and uses bounded diagnostic text. Hard external/transient storage, complete monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. In `proposal_owner_process.py`, a publication write could fail, close could also fail, and the subsequent file-length observation could replace the original error. An overridden exception `repr`, `add_note` or truthiness method could interrupt observation or error annotation. Selected failure-counter updates could also replace the failure they were recording.

The monitor now retains the first failure and independently attempts publication close and the final file-length observation. If the body succeeded, the first finalization error escapes. If the body failed, it continues to raise the same exception object and annotates secondary errors. A close-attempt accounting failure still allows the close and its outcome accounting; close failure still allows the file observation. Selected operation-failure and unknown-progress counters are best effort while handling an existing error. Normal attempted/completed/failed counters retain their names and meaning. No missing counter is represented as a successful measurement.

Monitor error strings and secondary notes reuse the [existing helper diagnostic policy](Tower-Loadout-Placement-Failure-Diagnostics.md): at most 4,096 code points per selected string/note, four represented arguments, string arguments clipped to 256 code points before representation, and note additions only below a total count of eight. Native exception descriptors and exact built-in operations bypass custom formatting, attributes and note methods. Explicit `is not None` checks select process/runtime errors without calling exception truthiness. The original exception object and traceback propagate; diagnostic strings may be normalized or truncated. The Windows helper is now imported alongside the Windows monitor, so it is available across its reporting paths. Earlier imports remain outside monitor accounting.

These changes cover the monitor's selected operation counters, legacy hash-failure counter, publication finalizers, process snapshot, runtime-error selection, terminal snapshot, terminal persistence and publication-result error handling. They do not change the internals of nested accounting, runtime-environment or monitor-I/O modules: an internal failure in those modules can still replace an error before it reaches the monitor. Input exceptions, argument graphs, traceback frames, existing notes, blocking OS calls and full monitor memory/lifetime remain outside the bound. No new receipt schema, resource limit, configuration option or scientific admission is introduced.

A failed monitor-I/O scope remains unusable. In the retained fixture, a real literal worker exits and its job drains with every acquired handle closed. The test then injects a partial observation write, an error after the real publication close, and a file-observation error. The original write exception survives all three stages without any custom exception hook calls. The in-memory terminal snapshot accurately reports failed publication and unknown partial-write progress. Its terminal-file publication is rejected by the existing failed-scope guard. The fixture exporter saves that memory snapshot and failed publication result separately as test evidence; those files are not production terminal persistence or a completed owner-observation package.
