# Three-reference positive-tie implementation

23 September 2026. Target: offline `LL/tools/BalanceHarness`. The [frozen comparison design](Tower-Practical-Three-Reference-Tie-Comparison-Plan.md) and opt-in selector are implemented. **241 backend tests and 18 Python tests passed.** The [captured-runtime admission](Tower-Practical-Three-Reference-Tie-Admission.md) is now complete; the [single scientific comparison](Tower-Practical-Three-Reference-Tie-Comparison-Execution.md) is now verified and closed as **`NoSelectorDifferences`**. Implementation tests establish behavior; the separate execution report records scientific evidence and its limits.

## Changed behavior and files

[TowerBossStudyPolicy.cs](../LL/tools/BalanceHarness/TowerBossStudyPolicy.cs) adds `tower-staged-three-reference-tie-v1`. It retains the designated primary on a positive maximum tie. If that primary is below the maximum, it prefers the first tied supplied reference in the frozen nominee order over a tied challenger. Strict win leaders and zero-win health ordering are preserved. Selection-row order cannot change the result. The supplied set is obtained only from the validated definition; the raw-input overload rejects this policy without the required binding.

[TowerBossDiscoveryContract.cs](../LL/tools/BalanceHarness/TowerBossDiscoveryContract.cs) restricts the opt-in to the direct three-reference generator, exact supplied recipes, one root/context, all five nominees and one finalist. Existing primary designation in confirmation metadata continues to describe the designated reference; the actual selected team is recorded separately in the finalist. No historical fitness or confirmation outcome enters the selector.

[TowerIncumbentTieProtocol.cs](../LL/tools/BalanceHarness/TowerIncumbentTieProtocol.cs) defines the new comparison profile while retaining the old defaults. [The comparison controller](../LL/tools/BalanceHarness/TowerIncumbentTieComparison.cs) runs 24 shared searches, compares both selectors on each common matrix, freezes all 48 outputs and confirms only differing recipes. The new profile uses **12,672 +2,000K fights**, at most **60,672**, and keeps the fixed **24,000** denominator, **+1-point /240-net-win** gate, three-positive-root requirement and positive conditional lower bound. Identical outputs have zero difference and null absolute wins. The original two-reference profile keeps its 11,904 search fights and original decisions.

[Reservation validation](../LL/tools/BalanceHarness/TowerIncumbentTieReservation.cs) binds the reconciled three-reference capture, exact plan and auditor, sorted complete history and explicit cumulative resource fields. The new request uses `tower-three-reference-tie-comparison-v1`; its additional fields are `captureCloseoutRoot`, `planPath`, `planHash`, `auditorPath`, `auditorHash`, `priorSeconds` and `priorBytes`. Null fields are omitted from legacy serialization. One 32,768-word batch reserves every fresh word, assigning 984 search values and 24,000 confirmation values. Exhaustion, cancellation and checkpoint failure preserve the exposed reservation without refill.

[Archive reconstruction](../LL/tools/BalanceHarness/TowerIncumbentTieArchive.cs) rebuilds generation, both selectors, the freeze barrier, recipes and paired panels from saved battles. [The native run boundary](../LL/tools/BalanceHarness/TowerIncumbentTieRun.cs) validates version-specific limits and owned process receipts. [Program.cs](../LL/tools/BalanceHarness/Program.cs) documents the two launchers. Native commands retain the existing `tower-incumbent-tie-comparison-` prefix; the new version additionally supports the read-only `-audit` command before publication.

[The independent auditor](analysis/audit-incumbent-tie-comparison.py) separately recounts direct outcomes, physical recipe identity, both selection choices, the global barrier and conditional arithmetic. It supports the old sealed-archive mode and the new working/completed archive modes. Native replay additionally verifies deterministic proposals and exact .NET hashes. [The new launcher](../build/run-three-reference-tie-comparison.py) includes native replay, independent audit and final publication within the same remaining **10,200-second /5.5-GiB** execution envelope, after the fixed **600-second /512-MiB** admission charge. It requires all resource fields explicitly. Final storage accounting includes completion and manifest bytes. Failed audits cannot publish or trigger retries. The original two-reference launcher is unchanged.
