# Loadout placement: bounded monitor receipt encoding

Current status: selected monitor receipt encoding bounds string chunks, container depth and output-relative temporary work. Hard external/transient storage, whole monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. The previous monitor I/O implementation checked each `JSONEncoder.iterencode` result against the remaining publication allowance only after the encoder had created that token. A large string could therefore allocate a large escaped token before the byte check rejected it. This change closes that selected encoding gap without claiming a whole-process memory limit or filesystem isolation.

`proposal_monitor_io.bounded_canonical` now produces the selected monitor receipts. The existing per-publication and remaining total write allowances bound its output payload. It sends at most **1,024 Unicode code points** at a time to the standard string encoder, producing at most **6,144 UTF-8 payload bytes** per chunk, excluding the temporary surrounding quotes. Control characters, quotes, backslashes and multibyte characters retain the previous escaping and bytes. Dictionary keys remain sorted and separators remain compact. The standard library still supplies string escaping and finite-float formatting; see the [Python JSON documentation](https://docs.python.org/3/library/json.html).

Before allocating sorted key lists or traversing containers, conservative minimum-output checks reject values that cannot fit. Dictionary key lengths are checked before sorting. A hexadecimal digit-count lower bound rejects clearly oversized integers before decimal conversion. Decimal conversion still uses the interpreter's own safeguards. Container nesting is limited to **64**, and circular references are rejected while repeated shared subtrees remain valid. Only exact built-in dictionaries, lists, tuples, strings, integers, finite floats, booleans and `None` are accepted; dictionary keys must be exact strings. Type checks use identity so custom metaclass equality cannot impersonate a supported type or invoke a hook.

These are constraints on selected encoding work. Input objects already exist before encoding. The output bytearray and final bytes copy coexist, sorted key lists and integer text depend on the byte allowance, and Python's allocator adds overhead. No numeric allocator/RSS ceiling, bound on input construction, complete monitor-memory bound or elapsed-time bound is established. `memoryBounded`, `wallClockBounded`, `wholeProcessCoverage` and `usableForAdmission` remain false. Other JSON producers are outside this change.

All monitor I/O v1/v2 publications use the encoder, including the optional `monitor-call.json` terminal file. The declaration and receipt schemas are unchanged. Supported receipt values produce byte-identical canonical output. Custom subclasses, non-string keys and nesting beyond 64 now fail explicitly; current monitor receipts use the supported representation. Encoding failure occurs before publication open and before a write-byte reservation is accepted, and poisons the monitor I/O scope. Existing reservations from earlier work are retained. The default monitor path without an I/O budget is unchanged.

The same module's hash-close path also used `sys.exc_info()` in a way that could see an exception already handled by its caller. A new close failure inside that caller's `except` block could then be suppressed, incorrectly allowing `hashCompleted` to increase. The hash operation now records only its own body exception. Close failure remains a failure, the opened stream receives its close attempt, the read reservation is retained and a prior read failure remains primary.
