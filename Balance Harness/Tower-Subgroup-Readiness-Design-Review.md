# Four-party evaluator reuse and readiness design

**Use the existing general `tower-balance-run` path, with an isolated comparison-decision adapter. Do not adapt the dedicated `TowerCompleteFamily` controller or implement another search generator.** This source review identifies a practical route for the [four-party subgroup matrix](Tower-Subgroup-Matrix-Design-Review.md). It does not establish executable readiness or authorize combat.

## Exact comparison decision

Keep the preceding matrix and all four predeclared contrasts unchanged: **AB−AA, AB−BB, BA−AA, BA−BB**. All four parties are explicitly supplied recipes; use `reference` for generic evaluator provenance and keep candidate/anchor labels in comparison metadata. No recipe is newly generated by this adapter.

The frozen outline allocates alpha **.025 across four win-rate intervals** and **.025 across eight discordance-probability intervals**. Thus the two-sided per-interval alpha values are `.025/4` and `.025/8`; critical values are `PhiInverse(1 - alpha/2)`. In the existing generic `.05/family` Wilson formula these correspond to correction parameters **8 and 16**. Those parameters do not mean eight or sixteen actual recipes. The generic four-cell report's default correction is not the specified promotion correction.

For each candidate/anchor pair, join outcomes by the verified common trial key and seed. Count candidate-only wins as gained and anchor-only wins as lost; draws are non-wins. The paired interval is `[lower(gained)-upper(lost), upper(gained)-lower(lost)]` using the fixed discordance correction. Reject mismatched identities, duplicate or missing keys and incomplete panels before computing it. Do not assume that merely zipping two arrays establishes pairing.

A candidate passes only when both paired lower bounds are strictly positive, its corrected win-rate lower bound is at least **10%**, and both observed gains are at least **five percentage points**. With 256 outcomes, the exact gain check is `100*(gained-lost) >= 5*256`, requiring **13 net wins**. Never compare rounded displayed percentages. Both candidates may pass; that does not establish superiority between them. The four-way interaction remains descriptive and creates no extra significance test.

The existing audited interval approach is approximate. This review checks its intended algebra and API correction factors, not numerical implementation or statistical power. A future adapter needs literal and independent arithmetic verification before use. The generic balance report remains preserved alongside the improvement decision; no above-50% recipe is removed to make balance pass.

## Smallest proposed next scope

Implement one isolated Python adapter that reads this [frozen contract](../TestResults/balance/tower-subgroup-readiness-design-20260916/adapter-contract.json), the existing seed-free matrix, and an explicit four-party outcome export. It should validate identity/completeness/pairing, calculate the fixed corrected intervals and decision, and emit a small auditable receipt. Its preflight output should list which runtime, binding and native checks are still missing. No production C# change is justified by the inspected route.

Verify literal outcome matrices covering all draws/all losses, identical teams with nonzero interval width, complete reversed order joined by key, missing and duplicate keys, the exact 12-versus-13 net-win boundary, a large supported advantage, a candidate that beats only one anchor, both candidates passing, and a complete high-win family whose generic balance decision fails. A separate implementation must reproduce every interval and final gate. These are mechanical checks, not evidence of party strength. Historical AB's 4/8 discovery result must not tune the adapter or the gate.

The proposed scope is **30 seconds /1 MiB**, including preparation, source/output, failed work, cleanup and publication: ten seconds /384 KiB for frozen inputs and adapter; ten seconds /384 KiB for literal checks and independent audit; ten seconds /256 KiB for publication/preservation. It includes **no builds, backend tests, native preparation, new balance values, model fitting or combat**. A failed integrity or fixture check stops readiness. Passing these checks still does not admit a native runtime or authorize the 1,024-fight comparison.

After this source-review scope, only **1.525880 engineering seconds /443,128 engineering bytes** remain. The proposed next scope therefore requires a separately approved **30-second /1-MiB transfer from unused run capacity to engineering**, with no overall increase. Proposed component caps would be engineering **1,605 seconds /672,137,216 bytes**, run **1,695 seconds /368,050,176 bytes**, audit unchanged. This transfer is **not applied** by this review. No fresh-seed or combat approval is requested here.
