# Loadout placement: native pending declarations through the supervisor

Current status: the opt-in supervisor now binds, dispatches and retains explicit pending-storage declarations for all three native phases. Audit and publication phases prohibit pending writers. A complete dynamic native path inventory, lease bounds, runtime/cache bounds and the finite observer obligation remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. `StudyWorkSupervisor(..., native_pending_budgets=...)` requires exactly `native`, `nativeAudit` and `publication`, together with the existing three managed retention scopes and bounded persistent worker sidecars. It copies declarations at construction, validates phase/output restrictions before start, and seals the plan inside the existing `storage-binding.json` before dispatch. The plan includes a canonical declaration hash and explicitly sets `pathInventoryComplete=false`.

Native worker binding v6 and work receipt v3 carry this phase contract. Native declarations contain finite target-adjacent `.pending` paths under the study output. Captured content, source and executable roots, launch/admission inputs and worker identities/sidecars are protected from overlap. Audit and publication declarations must contain an empty file list and zero live/lifetime allowances. An attempted pending create in either phase fails before its create factory runs, even if it would write zero bytes. The independent Python worker keeps its existing v4 binding and receives no native declaration.

The existing per-file, creation-count, live-byte and lifetime-write checks still enforce declared native writes. Undeclared writes fail closed. The supervisor checks its sealed declaration before dispatch, prevents phase reuse, and retains each worker's validated observation. Its final `nativePending` observation distinguishes complete, failed, missing and not-invoked phases. Copies of cumulative counters are not added together. A failed or missing native receipt cannot produce a successful owner closeout.

V1 through v5 defaults remain unchanged. V5 still requires a nonempty pending list; only v6 introduces the explicit no-writer phase. The internal pending scope accepts an empty list only when explicitly enabled with both caps zero. No additional sidecar is introduced. A failed plan validation leaves the supervisor unvalidated, so callers cannot catch that error and proceed with `start`.

Source review found that the six allocation destinations are only part of native pending work. `TowerProposalStudy.Save` delegates to `TowerCompleteReservation.Storage` for nested study endpoints as well as final native receipts. The `Execute` callback emits placement catalogues, pair results, freeze/summary files and recipe-dependent held-out names. A six-file allocation declaration therefore cannot cover a complete native study. This implementation carries caller-supplied finite declarations; it does not generate or certify a complete scientific inventory. The native tests exercise an actual nested `Save` and prove that an omitted nested target is rejected. Audits and publication use explicit no-writer contracts, without invented placeholder filenames.

No scientific launcher default, admission check, compressed guard, gameplay value or search policy changes. Optional supervisor activation requires updated captured accounting sources and a runtime supporting v6. It establishes cooperative enforcement for declared pending writers, not confinement or bounds on raw APIs, metadata, retained destinations, leases, serialization memory, external mutations, runtime caches or observer work. `wholeProcessCoverage`, `usableForAdmission`, scientific admission and runtime qualification remain false.
