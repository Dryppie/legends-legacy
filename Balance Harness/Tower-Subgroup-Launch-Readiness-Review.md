# Four-party launch preparation

The launch wrapper and reservation checks are implemented and verified with retained fixtures. This completes the authorized preparation scope. No fresh seeds were derived or reserved, no native executable was launched, and no combat ran. No stronger team has been established.

The [launcher](../TestResults/balance/tower-subgroup-launch-readiness-20260916/launcher.py) supports `prepare` and `run`. Preparation accepts an externally reserved panel and its exact file hash, verifies its ordered journal and the frozen context, then materializes the unchanged four-cell definition. It writes a plan containing exact argument arrays, input hashes and a fixed output directory. It neither generates random values nor treats a plan as permission. Execution requires a matching plan hash and `--execute-authorized-comparison`, supplied only after separate user authorization.

The [contract](../TestResults/balance/tower-subgroup-launch-readiness-20260916/launcher-contract.json) pins the admitted 26-file runtime, dotnet host, captured content, protocol, owned-process helper, authoritative historical ledger and 196 known history files. The ledger reconstructs exactly 483,732 distinct excluded values. The existing historical sources must remain unchanged. The later reservation scope must also reconcile any newly created ledger sources; this scoped check does not claim a live repository-wide registry scan. V19's 512 unused values remain excluded, its 253 required recipes remain Unresolved, and adoption remains Hold.

The required reservation JSON has exactly `kind`, `reservationState`, `protocolSha256`, `historicalLedgerSha256`, `exclusionsSha256`, `samples`, `trialKeys` and `journalSha256`. Native reservations use `SubgroupReservedPanel` and `Complete`. Samples are 256 unique int32 values disjoint from the reconciled history; keys are 256 unique nonempty strings. The newline-terminated journal has exactly 256 ordered records, each containing `index`, `seed` and `trialKey`. It records an externally completed reservation; these fields and hashes do not authenticate permission, independent sampling or a particular allocation algorithm. The future reservation must be durably recorded and independently checked before this wrapper consumes it.

The wrapper preserves the protocol's four complete parties and common 256-value panel, 1,024 attempts, zero retries, fixed Essence order and unchanged success rule. It uses the generic native CLI, which validates the complete family and creates every party input before the first fight. Native structural/materialization validation will therefore occur on the exact future panel before execution can begin. No separate new search algorithm or native helper build is required by this wrapper.

Execution takes a create-new, durable launch claim before creating a process. A second invocation cannot replace that claim or resume incomplete evidence. The child is created suspended and assigned to the retained Windows Job Object before it runs. The enclosing 1,000-second allowance includes measured preparation and preflight time; native execution remains capped at 900 seconds. The wrapper observes the whole owned directory, including temporary files and logs, with a 60-MiB ceiling and 32-KiB receipt reserve. Timeout or storage failure terminates owned work and retains the failure. No failed attempt authorizes a retry.

The fixed command arrays are constructed from pinned paths, with no shell interpolation. The [command fixture](../TestResults/balance/tower-subgroup-launch-readiness-20260916/command-fixture.json) demonstrates argument boundaries for paths containing spaces. The future native verifier command is included in the plan. Exit 0, 1 or 3 produces only `AwaitingNativeAudit`; it never authenticates outcomes. Exit 2, timeout and other execution failures are rejected. The prior extractor, native archive reconstruction and independent attempt audit remain required under the frozen 145-second /8-MiB audit envelope. They must verify the producing runtime and unchanged archive manifest before any strength decision.

The previous storage estimate omitted the temporary launch definition. Keeping it alongside the completed archive would estimate **64,988,077 bytes**, above the 60-MiB ceiling. The wrapper instead verifies the native frozen-files manifest and exact semantic equality, records both hashes, writes the extractor's native-file binding, and removes only its own temporary source. The full definition remains in the native archive and the original bytes can be reconstructed with the wrapper's canonical JSON serializer. No sealed evidence is removed.

The [revised phase calculation](../TestResults/balance/tower-subgroup-launch-readiness-20260916/storage-phases.json) estimates **42,924,069 bytes** at startup and **60,917,160 bytes** afterward. Both fit the cap and receipt reserve. The report-size factor is still an estimate from a different retained cohort. If observed output crosses the ceiling, execution stops and remains incomplete; the polling guard is not a promise that actual output will fit or cannot briefly overshoot.

Verification ran through the bounded `workflow.py input`, `checks`, and `publish` phases. All fixture sample values were already reserved historically; their reduced fixture history never entered the native launch path.
