# Loadout placement: owned job memory and process limits

Current status: optional Windows Job Object limits constrain the owner/descendant job's committed virtual memory and concurrent process count. Monitor/caller memory, hard external/transient storage and complete observer/cleanup lifetime bounds remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. `bounded_windows_process.run(..., job_limits=declaration)` and `OwnerProcessMonitor(..., job_limits=declaration)` accept `tower-owned-job-limits-v1` with `maxJobCommitBytes` and `maxActiveProcesses`. Values must be strict positive integers; commitment bytes must be page-aligned and fit both the native pointer-sized field and signed-64-bit range, while the active-process ceiling must fit a DWORD. The declaration is copied before job creation. Defaults remain unchanged, and these caller-supplied diagnostic limits do not set scientific admission limits.

The helper installs the memory and active-process limits while retaining kill-on-job-close and prohibiting breakaway. It queries the job to verify the exact flags, commitment ceiling and process ceiling before creating the suspended owner. A failed set, failed query or mismatched value prevents process creation and log creation. The owner is then assigned before resume as before. No failure falls back to unlimited execution.

The memory limit covers the job-wide sum of committed virtual memory. Requests beyond it fail; it is not a resident-memory or total-host-memory ceiling. The process limit controls simultaneous job members, not lifetime process creations. Windows documents these behaviors in its [basic job limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information) and [extended memory limits](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information). Descendants inherit membership, and nested jobs cannot relax an ancestor's applicable commitment limit; see [nested jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

An optional `tower-owned-job-limits-observation-v1` block records the copied declaration, whether setting succeeded, whether readback verified it, the verification boundary and any setup error. The owner monitor binds the plan and rejects missing or changed configuration observations. The common owner ledger validates the block and rejects completed/assigned process observations with unverified limits. Setup failure remains distinct from an executed process. Existing memory high-water and job I/O records retain their own measurement boundaries; none are added together as a new memory or storage budget.

The observation deliberately does not count violations. A program may handle a refused allocation and still exit zero, and a process-creation failure does not itself establish scientific failure or success. We do not add completion-port notifications in this change. The monitor process remains outside the newly created job, and these limits do not cover its memory, kernel buffers, resident/shared memory, physical/pagefile storage, arbitrary external writes, total process creations or complete elapsed/cleanup time. `violationsObserved`, `monitorMemoryBounded`, `totalProcessCreationsBounded`, `wallClockBounded`, `filesystemConfinement`, `wholeProcessCoverage` and `usableForAdmission` remain false.
