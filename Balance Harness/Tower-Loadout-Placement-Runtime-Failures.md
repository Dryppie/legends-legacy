# Loadout placement: runtime inspection failures

Current status: runtime inspection preserves first errors, clears stale samples, attempts directory-iterator close and records final-sample failures in the correct monitor phase. Hard external/transient storage, complete monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. `RuntimeEnvironment.prepare` and `sample` previously formatted failures using the exception's class name and `str` method. Custom methods could raise while recording the failure and replace the original exception. Directory context-manager cleanup could also replace an iteration or metadata failure. Preparation did not explicitly invalidate a successful sample if a later preparation failure escaped. Separately, the monitor's final runtime sample ran outside its operation-accounting wrapper: a failure could be attributed to the later verification phase after incomplete evidence had been published.

The runtime inspector now records one of three fixed diagnostic strings, with a maximum of **73 code points**: preparation failure, inspection failure, or inspection plus directory-close failure. The strings deliberately omit exception details. The original exception object and traceback propagate to the caller, where the outer monitor can retain its existing bounded error summary. Runtime failure recording does not inspect exception arguments, class names, formatting methods, truthiness or notes. Existing caller-owned notes remain untouched. No new import dependency is introduced.

Every caught preparation or sampling failure marks the profile failed and clears its last sample. If the initial sample fails during preparation, preparation preserves that first diagnostic. Sample setup and final sorting are inside the protected failure boundary, so allocation failure cannot leave a previous sample presented as current. A failed profile still rejects later sampling and preparation without overwriting its first diagnostic or retrying I/O. Partial directories remain available for inspection; the runtime module does not erase them.

Each successfully acquired directory iterator receives one explicit close attempt. A body error remains primary when close also raises, and the fixed combined diagnostic records that both operations failed. A close-only error propagates and invalidates the sample. Failed acquisition has no iterator to close. Explicit close is not proof of successful release, and no retry or hard deadline is introduced. Metadata races, original exception/traceback memory, blocking OS calls, transient/external storage and complete monitor memory remain outside the contract.

The outer monitor now records its final post-drain sample as `runtimeFinalInspection` in the `ownerProcess` phase, using the existing attempted/completed/failed operation counters. This records failure before observation/publication advances the phase. Publication of incomplete evidence may continue, and the original runtime failure still escapes. Receipt schemas, runtime destinations, environment values, declared limits and scientific gates are unchanged.
