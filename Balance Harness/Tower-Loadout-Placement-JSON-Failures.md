# Loadout placement: accounted JSON failures

Current status: accounted JSON writers preserve first errors, attempt cleanup independently of accounting and retain failed receipt state even when failure counters cannot update. Hard external/transient storage, complete monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. Its shared accounting module has two JSON writers: `Counters.write_json_output` for auditor output and `OwnerFileCounters.write_json` for owner output. Failed-write accounting could replace the write exception. In the auditor writer, a failed close-attempt counter could prevent the close itself. In the owner writer, context-manager close and final file observation could replace an earlier serialization, write, flush or sync error. Failed-operation counters alone also could not reliably prevent a caught output failure from being reported as a complete receipt.

Both writers now retain the first exception and attempt exactly one explicit close for each acquired stream. Close accounting runs independently of close itself. The owner writer attempts its final file observation independently of close, then records the operation outcome. A raised observation error makes the operation fail; ordinary suppressed metadata errors retain their previous unknown-sample semantics. Failed acquisition has no stream to close. Failed-write and unknown-progress counters are attempted independently, and their failure cannot replace the original write exception. Successful JSON bytes, exclusive open, encoding, newline behavior and existing flush/sync behavior remain unchanged.

Each counter scope also retains an in-memory JSON-failed flag. The flag is set before the initial operation counter and restored only on fully successful return. Once a write fails, a later successful write cannot clear that state. Counter receipts therefore remain `Failed` even if the caller requests success and the failed-operation counter itself could not be recorded. The worker scope checks the same state before claiming completion. This changes failure handling in the accounting module imported by scientific owner/auditor code; no scientific command was executed. Receipt schemas and versions are unchanged.

Secondary failures add only one of four fixed notes, each at most **58 code points**. Additions stop when an existing exact list reaches eight entries. Nonstandard or already full note collections remain untouched. The helper uses the native exception dictionary and avoids custom exception formatting, truthiness, attribute and annotation hooks. Annotation failure is suppressed, and the original exception object still propagates. Existing note content, exception arguments and traceback memory are not bounded by this helper. Explicit close attempts do not guarantee successful release or impose a deadline on blocking calls.

Verification passes **728 Python tests in 32 groups**: **26 new cases** plus all 702 current regressions, with no retries or skips. New cases combine serialization/write/flush/sync errors, close errors, failed attempt/outcome counters and failed final observation. They also cover failed acquisition, completion-counter failure, failure state surviving subsequent success, unchanged successful bytes, hostile exception hooks, cancellation, caller exception isolation, bounded notes, annotation allocation failure and worker-scope rejection of a caught failure whose numeric failure counter is missing. One existing owner-writer fixture now opens and closes its fake stream through the explicit methods used by production; its assertions are unchanged.

The retained literal-worker fixture writes a partial `{`, then injects write, close-attempt accounting, failed-write accounting, overall failure-accounting and post-close errors. It retains the original write error, verifies one real close and records four fixed notes without invoking formatting hooks. Its counter receipt is `Failed` although `jsonOutputOperationsFailed` is absent. The parent confirms job drain and owned-handle closure. A successful fixture process means the fault assertions passed; it does not imply a successful JSON operation or scientific admission.
