## Implemented behavior

`tower-proposal-racing-v3` now accepts exactly `tower-proposal-policy-v3`. It requires the authored affinity inventory and validates both selected creation routes and any separately declared preservation routes. Old racing envelopes reject the new policy. Existing v1/v2 behavior and deterministic trajectories remain compatible.

The existing native adapter can execute and replay v3 through its owned API. Full generation evidence, including the target pair, edits and newly activated route IDs, participates in reconstruction. Both per-trial journals and panel-freeze journals are covered. Archive, runtime and complete reconstructed inventory bindings are checked before dispatch. Both comparison archives must pass preflight before the control spends any trial; an incomplete control prevents candidate dispatch. Started trials remain charged on failure or cancellation, and incomplete generation yields no selected output.

The new design identity is `tower-affinity-creation-comparison-v1`. Its control is the existing benchmark single-edit v2 factory. Its candidate is exactly `BenchmarkAffinityCreation(selectedIds)`: nine/eight creation slots, benchmark parentage and no preservation constraint. Policy, parent, schedule or selector changes cannot silently reuse this design. This tests the complete creation strategy against single edits; it is not a preservation ablation or proof of individual affinity strength.

Planning deterministically requires at least 17 distinct legal benchmark edits, enough for the two waves' nine/eight accepted slots. Equivalent owner/removal/addition edits count once even if multiple routes lead to them. This check uses legal structural possibilities, without generating proposals, previewing roots or drawing entropy. It does not guarantee that every stochastic run fills both waves within its existing attempt bound.

The public `tower-proposal-comparison-plan` command selects exactly one v3 candidate from a v3 export request, including the retained four-arm development request. Multiple v3 candidates are rejected. Plan output remains create-new. No public combat launch command was added.

The existing owned study controller, protocol and summaries explicitly remain preservation-only. They reject the creation design before writing or dispatching work. This boundary prevents a newly valid native plan from entering the old scientific controller and audits. Versioning that controller and its two audits is the next implementation step.

## Frozen prospective design

The plan retains the established comparison's measurement and resource rules:

| Item | Declared value |
| --- | --- |
| Independent paired roots | 12, all retained |
| Search budget | 528 trials per arm per root |
| Shared search panels | 8 / 8 / 8 / 8 / 40 values, plus one proposal root |
| Independent held-out panel | 256 values per root |
| Fresh allocation | 3,948 distinct values |
| Fight ceiling | 21,888 |
| Prospective time / storage ceiling | 10,800 seconds / 6 GiB |
| Output barrier | All 24 search outputs frozen before any held-out observation |

Both arms use the same proposal root and search panels, with separate search charges and archives. Identical physical outputs within a root share held-out measurement and have exactly zero method contrast. Search and held-out values are mutually isolated and excluded from declared historical values. There is no favorable-root screening, refill or replacement; any incomplete root invalidates the study.

The primary endpoint is the equal-root mean held-out candidate-minus-control win-rate difference. The guardrail is candidate-minus-fixed-benchmark. Report all 12 root contrasts and descriptive 95% t intervals, plus paired-seed uncertainty conditional on frozen outputs. These are not powered efficacy claims about future searches.

The decision order remains: incomplete; abandonment; no observed output differentiation; larger fresh evaluation warranted; otherwise inconclusive. Abandon when the mean method difference is at most −2 percentage points, or when the mean benchmark difference is at most −2 points and fewer than three roots select a promising novel output. A larger fresh evaluation requires at least +2 points over control, at least zero over the benchmark, at least three differing roots and at least three promising novel roots with gains of at least +3 points. No outcome directly promotes a gameplay or search default.

The plan was first created from the authenticated development request, then rebound by changing only the context's execution identity to the qualified runtime. All design fields except the resulting scope hash remained identical. It allocates nothing and does not establish that the proposed resource ceiling is sufficient or currently available.
