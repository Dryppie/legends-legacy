# Loadout placement: explicit runtime environment and inspection

Current status: optional owner process environments now replace inherited variables and declare seven temp/cache destinations with bounded metadata inspection. This is not filesystem confinement or a hard write quota. Hard external/transient storage and finite observer/elapsed-time obligations remain unresolved; both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. `OwnerProcessMonitor(..., runtime_environment=declaration)` accepts `tower-proposal-runtime-environment-v1` with `root`, `maxEntries`, `maxDepth` and `maxRetainedBytes`. The root must be fresh, beneath system temp, and disjoint from protected evidence. The profile creates seven directories: `temp`, `profile`, `roaming`, `local`, `dotnet`, `bundle` and `nuget`. Package-manager cache destinations stay outside the checkout. Production code retains these directories on success or failure for caller inspection; it does not recursively delete them or reuse stale roots.

The profile supplies a complete environment with named TEMP/TMP, user-profile/application-data, .NET CLI, bundle-extraction and NuGet destinations. Python bytecode writes and user-site imports are disabled, and .NET diagnostics and telemetry are disabled. The Windows directory comes from the OS API. Parent PATH, Python import paths, .NET startup hooks and unrelated parent variables are not merged into the profile. Ordinary child inheritance carries the owner environment into descendants; trusted code can still replace it or write to explicit external paths. The monitor's own process environment is unchanged.

These settings use documented controls: [Python environment options](https://docs.python.org/3/using/cmdline.html) cover bytecode and user-site behavior, while [.NET environment variables](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-environment-variables) identify CLI supporting-file and bundle-extraction destinations. They control selected runtime behavior, not all filesystem access.

`bounded_windows_process.run(..., environment=values)` also supports a complete explicit mapping. It validates and copies at most 128 ASCII variable names and at most 65,534 UTF-16 bytes, rejects duplicate names ignoring case and embedded NULs, sorts normalized names and builds a double-terminated Unicode block. Explicit environments require an absolute executable, so parent PATH cannot silently select it. The environment buffer remains alive through process creation. This follows the [CreateProcessW environment-block contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). Existing callers retain inherited environments and their original observation schema.

The helper adds `tower-owned-environment-v1` to the process observation: a hash of the creation block, variable count, encoded size and explicit coverage flags. It does not serialize arbitrary environment values. The monitor retains its fixed profile plan, module hash and expected block identity, then compares them with the helper's observation. The common ledger validates this optional observation and rejects stronger confinement or write-bound claims. The monitor's fixed profile values contain only known settings and declared paths. Plans are captured before dispatch and retained in the existing observation package, without an additional sidecar.

Named directories are inspected before process creation, during process checks and after confirmed job drain. Each sample has an entry allowance of at most 4,096, a depth allowance of at most 32, and a caller-declared retained-byte guard. Missing destinations, reparse points, unknown file types, metadata failures and exhausted allowances fail the inspection. Failed totals remain unknown. A periodic violation interrupts owned work; a final violation prevents a successful monitor outcome even if the child exited zero. Original failures survive secondary inspection/publication errors.

These are metadata samples, not write interception. A file may grow beyond the declared sampled-byte limit between checks, and a create-write-delete sequence may disappear entirely before a sample. Blocking metadata calls, arbitrary external paths, runtime/OS storage, environment overrides, monitor writes and complete cleanup time remain outside hard bounds. The tests explicitly demonstrate that a transient write can escape a sampled zero-byte total. `runtimeWritesBounded`, `transientWritesBounded`, `filesystemConfinement`, `wholeProcessCoverage` and `usableForAdmission` remain false.
