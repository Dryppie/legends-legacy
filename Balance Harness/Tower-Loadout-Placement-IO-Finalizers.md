# Loadout placement: monitor I/O finalizers

Current status: selected monitor hash/inventory finalizers preserve original failures, attempt resource close and avoid exception-formatting callbacks. Hard external/transient storage, complete monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. The bounded monitor-I/O module previously used an exception's `add_note` and `repr` methods after simultaneous hash-read and close failures. A custom method could replace the original read failure. Directory inventory used a context-manager close that could similarly replace an iteration or entry-limit failure. These paths sat inside the outer monitor's recently corrected failure handling, so the original error could be lost before reaching that boundary.

The module now makes one explicit close attempt for each acquired hash stream or inventory iterator. A body failure propagates as the same exception object even if close also raises. If the body succeeds and close fails, that close exception escapes and the I/O scope becomes failed. Failed opens acquire nothing to close. Inventory uses the iterator's explicit `close` method, which Python documents as releasing its acquired resources; exhaustion can also release them automatically. The implementation retains an explicit close attempt on every path after acquisition. [Python `os.scandir` documentation](https://docs.python.org/3/library/os.html#os.scandir).

Secondary close failures receive a fixed literal note identifying hash or inventory close, with their exception details deliberately omitted. Notes use the native exception dictionary descriptor and exact built-in dictionary/list operations. This avoids custom exception formatting, truthiness, attribute access, `add_note`, and list-subclass methods without introducing a Windows-launcher dependency into the pure I/O module. Added notes are at most **58 code points**. An existing exact list receives additions only below **eight** notes; full or nonstandard caller-owned collections remain untouched. Annotation allocation failure cannot replace the original error. Input exceptions, secondary argument graphs, traceback frames and pre-existing notes remain outside this diagnostic-payload limit.

The existing v1/v2 receipt schemas, read/write declarations and attempt limits are unchanged. Read reservations are not refunded after failure, unknown read progress remains unknown, and a hash is not marked complete if close fails. A failed scope still rejects later reads, inventories and publications. The code makes no retry and does not claim that a failed close released its resource. Blocking close/OS calls, full memory, external mutation and transient storage remain unbounded. Other accounting and runtime-environment finalizers are unchanged.

Verification passes **681 Python tests in 30 groups**: **23 new cases** plus all 658 current regressions. One existing hash-close assertion now expects the fixed note instead of the secondary exception message. New tests cover simultaneous read/close errors, close-only failure, successful hashing and its EOF probe, counter/metadata/open failures, caller exception isolation, cancellation, note-count limits, unsupported note collections, list subclasses, annotation allocation failure, large secondary arguments, inventory iteration/entry/limit/close/open failures, failed-scope reuse prevention, and an independent import that prohibits the Windows launcher.

The retained real-worker fixture drains a literal owner's job and closes all owned process handles, then injects a console-read failure and an error after the real stream close. The original read error survives, the stream receives one close attempt, and no custom exception hooks run. The monitor retains an in-memory failed snapshot with unknown read progress and no claimed owner-observation publication. The test harness exports that memory snapshot and the earlier process observation as diagnostic evidence; these exports are not a completed production monitor package or full-lifetime measurement.
