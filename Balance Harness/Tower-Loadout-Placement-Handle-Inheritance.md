# Loadout placement: explicit inherited standard handles

Current status: new owned-process launches inherit only stdin and merged output handles. Hard external/transient storage, whole monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. The shared Windows process helper previously set `bInheritHandles=True` without specifying a handle list. Any unrelated parent handle already marked inheritable could therefore reach a worker, including writable files. The helper now passes `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` with exactly two handles: its NUL stdin and its merged stdout/stderr destination. In bounded-capture mode the destination is the pipe writer; in default mode it is the log file. This follows Microsoft's documented [explicit handle-list mechanism](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

Every new helper launch uses `STARTUPINFOEXW` and `EXTENDED_STARTUPINFO_PRESENT`. Existing suspended creation, assignment before resume, kill-on-close job ownership, optional job limits and optional Unicode environment replacement remain in effect. There is no new caller option or observation schema. The helper stops on attribute setup failure and never falls back to broad inheritance. Microsoft's [CreateProcessW documentation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) describes the extended-startup flag and the default broad-inheritance behavior this change replaces.

The helper sizes one attribute list before allocation and rejects zero or more than **65,536 bytes**. This bounds that selected allocation, not complete Python or kernel memory. It verifies the expected sizing error, initializes the list, records both handles' previous inheritance flags, enables them and installs the list. The handle array and list storage remain alive through deletion. Initialization and lifetime follow the [Windows attribute-list API](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-initializeprocthreadattributelist).

On success or failure, restoration is attempted independently for every recorded flag, followed by one deletion attempt for the initialized list. An earlier exception remains primary; otherwise the first cleanup error is raised. Later errors become notes. If restoration or deletion fails after a suspended child was created, the existing unassigned-child cleanup attempts termination and closes the process, thread and job handles before any assignment or resume. A caller's already-handled exception cannot suppress a new failure.

This closes accidental inheritance at each call through this helper. It does not restrict the process token, prevent direct path access or handle duplication through other APIs, or enforce a disk quota. Temporarily inheritable standard handles can still be inherited by other launchers that use broad inheritance; descendants that bypass this helper are outside its handle-list rule. The monitor remains outside the owned job, and OS calls and cleanup have no complete elapsed-time guarantee. Filesystem confinement, transient-write bounds, whole-process coverage and scientific admission remain false.

Verification passes **599 Python tests in 26 groups**: **22 new tests** plus all 577 existing regressions. New cases inspect the exact list and startup layout; exercise sizing, initialization, flag-query, flag-setting, attribute-update, process-creation and cleanup failures; and verify cleanup after creation never resumes the child. Retained literal fixtures confirm exclusion of an unrelated inheritable writable file in both log modes, preservation of the parent's original handle, stdin EOF and merged stdout/stderr. A negative control deliberately uses the prior broad-inheritance behavior for a literal test process and demonstrates that the probe detects the inherited file. Regression fixtures cover runtime replacement, nested literal jobs, job limits, owner accounting and canonical monitor/terminal receipts. Development smoke runs are excluded from the final total.
