# Loadout placement: owner accounting finalizers

Current status: owner operation, copy and child-log scopes preserve first errors, complete final observations before success accounting and retain failed receipt state after caught or nested errors. Read/receipt finalizers, hard external/transient storage, complete monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. Three selected `OwnerFileCounters` scopes could lose an earlier failure: `operation` counted a failed action without protecting the original exception, while `copyfile` and `child_log` also performed final file observations that could replace it. The copy/log scopes recorded completion before those final observations. A caller that caught a wrapper failure could subsequently request a complete owner receipt, including when the numeric failure counter had itself failed.

The generic operation wrapper now preserves its action error if failed-operation accounting raises. Copies and child-log scopes retain their first error while independently attempting final file observation and failure accounting. They record completion only after final observation and final-byte accounting return. A raised final-observation error therefore makes the enclosing scope fail even if the underlying copy or process body returned successfully. Native copy internals and process cleanup are unchanged. Actual copied bytes, accepted return values, sampled file lengths and operation outcomes remain distinct evidence.

An owner-specific in-memory failed flag is set when any of these three scopes raises and is never reset. Owner receipts combine it with the existing JSON failure state while preserving the base receipt argument validation. A caught nested failure cannot be erased by a successful outer action, later copy, later child-log scope or later JSON write. Numeric counters remain best-effort diagnostics; a missing failure counter does not imply success. Receipt versions and schemas are unchanged, and successful outer operations may still have completed counters even when an earlier nested failure makes the overall receipt failed.

The existing bounded annotation helper is reused with two fixed owner notes, each at most **63 code points**, and the same eight-entry ceiling for exact note lists. It does not invoke custom exception formatting, truthiness, attribute or annotation hooks. Existing full or nonstandard note collections remain untouched. Annotation failure cannot replace the first exception. Exception arguments, original notes and traceback memory remain outside this bound.

Successful behavior is preserved: file copies still overwrite and return the original copy API result; false and `None` action results remain successful API calls. Returned timeout and nonzero child-process results still represent completed wrapper scopes, not successful children. Only logs marked as created by the current scope receive a final observation. The created flag is set before its counter, so a created-counter failure cannot skip that observation. Metadata errors deliberately suppressed by `observe_file` retain their previous unknown-sample semantics and do not alone fail the wrapper. No new hard deadline, retry, quota or filesystem confinement is introduced.

Verification passes **760 Python tests in 33 groups**: **32 new cases** and all 728 current regressions, without retries or skips. New cases combine action/copy/log errors with failed counters and final observations; distinguish initial and final failures; verify retained partial copies, unknown progress, overwrite/return semantics and created-log ownership; and cover nested caught errors, later success, cancellation, generator exit, hostile hooks, note limits, annotation allocation failure and receipt validation. Existing regression assertions are unchanged. Regression process tests also retain the timeout/nonzero-result semantics.

The retained real-process fixture runs a literal worker and verifies its zero exit, job drain and owned-handle closure. The process observer then raises; the final log observation samples the file before raising another error; failed-scope accounting also raises. The original observer error survives. Evidence retains that event order, two fixed notes, the process observation and a `Failed` owner receipt with neither a completed nor failed child-log-scope counter. The process observation precedes the injected observer error, so its successful process fields do not describe the enclosing accounting scope as successful.
