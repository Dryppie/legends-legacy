# Loadout placement: bounded launcher failure diagnostics

Current status: launcher failure diagnostics use bounded text and avoid custom formatting/note callbacks during cleanup. Hard external/transient storage, whole monitor/caller memory and complete observer/cleanup lifetime remain unresolved. Both compressed guards and the 1,806/1,800-second gate stay closed.

The target is the offline Balance Harness. Its shared Windows process helper previously used `str(error)`, `repr(error)` and `error.add_note(...)` while collecting errors and closing handles. A custom exception could raise from those methods, replacing the original failure or interrupting subsequent closes. A very large argument could also allocate an unbounded formatted message. Python's [data model](https://docs.python.org/3/reference/datamodel.html) permits custom representation and attribute methods; exception [arguments and notes](https://docs.python.org/3/library/exceptions.html) are distinct from the original exception object and traceback.

The helper now reads arguments through the native `BaseException.args` descriptor and formats only exact built-in scalars. Single-string messages remain unchanged up to **4,096 Unicode code points**. Other messages use a class/argument summary with at most **four arguments**. Each represented string is clipped to **256 code points before `repr`**, and integers larger than **256 bits** use a literal marker before decimal conversion. Class names are limited to 128 code points. Custom metaclasses use a fixed class label; unsupported objects and scalar subclasses use literal markers without invoking their methods. Combined output is capped at 4,096 code points with a visible truncation marker. A formatting failure produces a fixed fallback string.

Secondary notes use the native exception dictionary descriptor and exact built-in dictionary/list operations. They bypass overridden `add_note`, attribute and list methods. Each note is at most 4,096 code points, with a 128-code-point prefix allowance. The helper appends only while the existing note count is below **eight**. It leaves full or unsupported caller-owned note collections intact without inspecting their elements. Annotation is best effort: a failure cannot replace the primary exception or stop later cleanup. Cleanup error records remain available independently of secondary notes.

These changes cover the helper's startup restoration, pipe/log cleanup, job-limit errors, job I/O and memory-query errors, handle-close errors and final observer error text. The original exception identity and traceback still propagate. Ordinary short single-string messages retain their text; compound and special exceptions can have normalized diagnostic text, including omission of fields outside `args`, such as an `OSError` filename. Captured helper hashes identify the producer, and existing observation schemas are unchanged.

The limits constrain selected diagnostic construction. Input exception objects, argument graphs, traceback frames and pre-existing notes already exist outside this bound. The helper does not shrink or replace those objects. Temporary string work depends on fixed argument/text limits, but allocator overhead and whole-process memory are not numerically bounded. Other modules' exception formatting, OS calls, observer callbacks and caller lifetime remain outside this change. Filesystem confinement, whole-monitor memory, complete elapsed-time coverage and scientific admission remain false.
