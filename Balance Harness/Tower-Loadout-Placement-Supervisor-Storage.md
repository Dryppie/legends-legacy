# Loadout placement: supervisor storage ownership

Current status: opt-in declared storage now covers the supervisor's owner, publication and terminal directories. Verification passes 403 Python tests; unchanged native sources/runtime retain authenticated prior 212-test backend verification. Original worker sidecars/logs, native pending/lease files, runtime/cache paths and the remaining observer lifetime are still unresolved. Both compressed guards and the 1,806/1,800-second resource gate remain closed.

The target is the offline Balance Harness diagnostic supervisor. `StudyWorkSupervisor(..., storage_contracts=...)` accepts exactly three declarations named `owner`, `supervisor` and `terminal`. Each uses the existing `tower-proposal-diagnostic-storage-v1` contract. Existing calls keep their prior managed-storage behavior and observation schema. The diagnostic storage implementation, retained owner, scientific launcher, native sources, process monitor, worker publication code and game services are unchanged.

All required retained members must be declared before any directory is created. These include owner/worker bindings, worker counter receipts, process observations, publication receipts, optional v3 publication-persistence receipts, final owner and supervisor observations, and manifests. Missing declarations or scratch roles on required retained files reject construction. Callers may declare additional managed scratch names. Limits are copied on construction so later changes to the caller's input cannot replace them.

The supervisor authenticates the captured diagnostic storage module alongside its existing source checks. It then creates the fixed directories outside the admission package and registry. The owner receives its own contract and protected paths; both publication directories use `DiagnosticStorage`. The supplied caps therefore apply to retained copies of worker sidecars as well as the supervisor's own evidence. They do not restrict the workers' original sidecar writes.

A new retained `supervisor/storage-binding.json` is written after the first enclosing resource check is installed and before worker dispatch or lease acquisition. It binds the canonical three-contract declaration, the supervisor/accounting/storage source hashes and the fixed relative scope roots. The supervisor manifest includes this binding. Changing the resource check for the audit phase does not rewrite it.

After terminal publication and verification, the opt-in terminal observation adds `storageOwnership`. This validates all three managed directories, the retained binding and the supervisor root's top-level membership. It contains per-scope storage observations and cumulative counter snapshots, plus the sums of declared live, scratch and total-write caps. Those sums are conservative bounds for the three disjoint cooperative directories only. `simultaneousPeakBytes` remains null: summing individual peaks does not establish a simultaneous peak. The new cumulative counter snapshots overlap earlier owner/publication records and must not be added to them.

Failure to write the binding prevents worker dispatch. A cap failure while retaining a worker sidecar stops subsequent workers. Later owner/supervisor/terminal failures prevent a success result or success manifest reference while retaining earlier evidence. A worker error remains primary if later publication also fails. The default launcher retry guard still rejects reuse before a second supervisor attempt.

The storage contract remains cooperative, with no filesystem confinement. An original worker receipt or external cache can grow and disappear outside the three directories. The final record explicitly lists worker originals, worker logs/study files, native pending publication/leases, runtime/external caches, and terminal persistence/remaining observer lifetime as missing coverage. Whole-process and admission flags stay false. The finite external-observer closure requirement is unchanged.
