# Boss-specific Essence loadout implementation

This guide describes the legacy schema-1/2 boss-search workflow in the offline `LL/tools/BalanceHarness` and local Tower Lab's **Historical reference refinement** mode. The dashboard now defaults to **Discover teams from scratch**, documented in the [independent discovery guide](Automatic-Tower-Team-Discovery-Implementation.md) and [Tower Lab review](Automatic-Tower-Team-Lab-Review.md). Independent discovery, staged confirmation and dashboard integration are implemented; the [fixed floor-1 and floor-5 pilots](Automatic-Tower-Team-Pilot-Review.md) are complete. Implementing the tool does not establish a winning loadout or a superior search method.

**Balance acceptance clarification, 11 September 2026:** the user approved a [10–50% Tower policy](Tower-Balance-Acceptance-Policy.md), requiring at least one build at 10% or higher per floor and no evaluated build above 50% at its intended progression budget. The legacy search maximizes paired victory gains and retains strong builds, including those above that ceiling. `Complete` and archive verification establish execution/evidence status only. The separate `tower-balance-evaluate` evaluator and independent `tower-boss-study` acceptance workflow are implemented; legacy reports retain their original semantics. Do not describe 10/10, 20/20 or 40/40 results as accepted difficulty or weaken candidate selection to bring reports into the band.

The subsequent [controlled pilot](Boss-Specific-Essence-Loadout-Pilot-Review.md) adds actual comparison evidence and [five complete reviewed recipes](Boss-Pilot-Recipes-20260910/README.md). Its schema-1 contracts allow up to 32 controls and 64 finalists. The sealed pilot keeps its original algorithms, reports and evidence.

New plans use `tower-boss-search-v2`. Portable catalogs retain **130 distinct historical recipes**: 42 for Eydis at five slots, 35 for Kodoku at four slots and 53 for Nhalia at seven slots. Every original pilot recipe remains, with its complete 20-sample observations kept separately from the later 40-sample refinement observations. Matching plans include every retained finalist and the catalogs' seed exclusions. Exact identities, gear and required party size must match; historical observations remain explicitly historical when content, execution or settings differ. Other boss/budget combinations use their authored controls. Schema 2 permits up to 64 controls and 96 finalists within the existing 100,000-fight per-study cap.

## Local workflow

```powershell
./build/run-tests.ps1 -Filter 'FullyQualifiedName~BalanceHarnessTowerBoss|FullyQualifiedName~BalanceHarnessTowerDashboardBoss'
dotnet run --project LL/tools/BalanceHarness/BalanceHarness.csproj --configuration Release --no-build -- tower-boss-inventory --output TestResults/balance/boss-inventory
dotnet run --project LL/tools/BalanceHarness/BalanceHarness.csproj --configuration Release --no-build -- tower-boss-plan --floor 3 --slots 6 --intent add-clearing --effort coverage --seed 20260910 --output TestResults/balance/boss-plan.json
dotnet run --project LL/tools/BalanceHarness/BalanceHarness.csproj --configuration Release --no-build -- tower-boss-search --definition TestResults/balance/boss-plan.json --output TestResults/balance/boss-run
dotnet run --project LL/tools/BalanceHarness/BalanceHarness.csproj --configuration Release --no-build -- tower-boss-verify --run TestResults/balance/boss-run
dotnet run --project LL/tools/BalanceHarness/BalanceHarness.csproj --configuration Release --no-build -- tower-loadout-replay --run TestResults/balance/boss-run --battle trial-000001 --detailed
```

Inspect the costed plan before running an experiment. Output paths must be new. Ctrl+C preserves completed trials, proposals and partial results; partial runs remain unconfirmed. `tower-dashboard` exposes the same workflow through a boss selector, explicit budget presets, optional intent, cost preview, run/cancel, report, exact recipe export and replay. It uses the existing local session protection and one-worker queue.

For a matching historical budget, open **Inspect retained recipes and historical results**. The selector loads a compact list; selecting a recipe loads its complete party, all-floor matrix and separate earlier observations. Export retains that observation's original target seeds, so replaying it adds no fresh evidence. Transfer rows require their recorded required allies; changing only the target recipe's floor does not reproduce those observations.

## Implementation and evidence boundaries

`TowerBossInventory` profiles all 15 released floors from guardian mappings and a typed graph of referenced abilities, statuses and summons. Source hashes and node definitions preserve conditions, triggers, targeting, scaling, stacking and caps. Counter intents and enabler/consumer compatibility remain hypotheses; unsupported runtime attribution is marked unknown.

`TowerBossSearchContract` adds `tower-boss-search-v1` independently of schema-1/2/3 generalist reports. It declares target weights, worst-context paired gains, allowed pool, mutable absolute character positions, shared controls, schedules, methods, generation seeds and actual-combat cap. Single-boss defaults search every required character on that floor. Later transfer-floor participants stay fixed. Four through ten slots use the existing explicit progression/gear presets; changing the slot budget changes the displayed preset.

`TowerBossOptimization` compares uniform legal random exploration, the existing structural beam/mutation proposal pattern, joint refinement and graph-pair refinement. All arms evaluate complete parties under the boss objective at equal candidate/sample cost, including shared controls. The legacy proposal arm is an adaptation under the new objective, not a reproduction of the historical multi-stage generalist algorithm. Retained generalist recipes remain mandatory controls.

Schema 2 records an explicit historical discovery-frozen anchor. New Eydis/Nhalia plans use the refinement's primary recipes (40/40 and 1/40 in that historical study); Nhalia's later-noticed 6/40 recipe does not replace its frozen primary. Kodoku retains its pilot anchor. Existing archives keep their original anchors and frozen catalogs. Guided fresh attempts alternate the anchor and the top four discovery parents, with every fourth attempt sampling a complete legal party globally. The legacy arm changes one character; joint refinement also changes two characters. The graph arm starts with the three predeclared mechanism replacements and then uses the same local refinement. Rejected and duplicate attempts are recorded. The random arm's distribution and random-number sequence are unchanged for identical starts and seeds. Default coverage/thorough plans add 8/24 new candidates per arm; the bounded refinement campaign declares its larger allocation explicitly.

Ranking uses worst-context weighted paired victory-rate gains on target floors, then target guardian health, survival, victory-only duration and stable recipe ID. Transfer floors never select candidates. The small strategy archive retains different measured behaviors among equal-primary-gain candidates. Mechanic totals never replace victory; an all-loss search stays unsuccessful.

Identical resulting ally contexts alias one effective evaluation. Their report rows share trial IDs and are not pooled. Shared starts are charged separately in every method/restart. Actual simulations and cache hits are reported separately. Proposal exhaustion marks the comparison incomplete instead of inventing equal-cost evidence.

Finalists, controls, behavior labels and the diagnostic quartet freeze before confirmation. Every selected party receives all 15 floors on fresh seeds. Separately reserved seeds measure a legal reference/enabler/consumer/combination quartet when available; otherwise the diagnostic plan records an unsupported reason. Confirmation and diagnostics never reselect recipes.

Schema-2 diagnostic recipes freeze before the first discovery fight. The typed activation graph selects an anchored baseline/A/B/AB replacement experiment, with each full Essence swap and its remaining effects declared. Eydis tests the existing Wound supplier and a separate recovery-to-protection replacement. Nhalia separately replaces a direct/periodic/lifesteal recovery supplier and a regeneration supplier with nonrecovery protection or pressure. Existing denial sources, fixed characters, source-family legality and conditional activation routes are checked. An unsupported mechanism produces an explicit reason instead of an unrelated Bleed quartet. Full Essence swaps have multiple effects, so the measurements support local recipe comparisons without isolating an individual mechanic's causal contribution.

Existing compact telemetry supplies summon presence, health deficit, prevention, reported healing and hostile action denial. Summon expiry is not an attributed kill; generated barriers are not absorbed damage; reported healing does not prove death prevention; aggregate denial does not identify its causal Essence. No combat observer changes are needed.

Schema 2 additionally reports effective regeneration by initial friendly participants and the initial guardian's reported healing and effective regeneration. These are target-fight means from existing statistics; they exclude summoned participants and are not fitness inputs. Nhalia's healing feedback must be inspected with both friendly recovery channels visible. `HealingDone` remains a qualified attribution field and must not be added to regeneration and described as effective recovery without further event-level validation.

Verification reconstructs inventory, contexts, proposals, objective scores, strategy retention, frozen selection, diagnostics and reports from saved fights. Export checks exact input hashes. Replay also requires the captured executable/runtime/platform identity and compares production outcomes and telemetry. Resealing an invented selection cannot bypass reconstruction.

The dashboard reuses reconstruction's compact battle previews and one serialized completed result. Every access still enumerates the archive and hashes every file; changed inventory/content invalidates reuse and triggers complete reconstruction. Returned objects cannot mutate the stored result. Reconstruction reuses a party input template only across consecutive seeds of the exact same scenario, while checking every seed's full input hash and arm-specific cache key. Selecting another saved run cancels the previous browser request, and loading displays elapsed time. This changes read performance without changing combat or archived report semantics.

Outputs include `boss-profiles.json/.md`, frozen definition/content/scope, context and seed ledgers, proposal histories, strategy archive, selection, diagnostic plan/results, all-floor confirmation, exact recipes, compressed reports and a hashed file manifest. `boss-search.md` explicitly marks observed transfer regressions with descriptive Wilson intervals and paired gained/lost counts.

## Measurement policy

This implements the machinery for steps 1–5. The controlled pilot screens four bosses across all seven budgets and performs deeper comparison in three selected cells. Broader boss/budget campaigns and the plan's conditional step 6 remain evidence-driven follow-up work. Calibrate runtime/storage before expanding comparisons. A graph proposal, strategy label or small test run does not establish a counter, synergy or superior method. Keep negative findings and frozen earlier evidence.

The accepted starter evidence and sealed whole-party study remain untouched. No migrations, production configuration changes, database application, deployment or Phase 2 integration are required.
