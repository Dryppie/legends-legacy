## Limits and failure handling

One parent process owns the output and the shared allocation lease. Its hidden worker has the same deadline, an independent parent-death/deadline watchdog, and no child processes. Preparation, full-history scanning, content/executable copies, search, native verification and publication all consume the same elapsed-time/storage allowance. Explicit prior costs are added, not reset. Two seconds and 4 MiB are reserved for closeout; already exhausted requests are rejected.

The existing full storage scanner checks all output files, including pending writes. The parent samples during execution and the worker checks execution boundaries; a write can cross the byte limit between checks. Such an overrun invalidates the run and preserves partial files. This is bounded-operation enforcement, not an operating-system disk quota. Completion is never accepted above the declared total. No whole-run performance improvement is claimed.

Every attempted battle is durably recorded before engine execution. Interrupted attempts consume their cap. Registration publishes Pending before the declared schedules can be used, preserves every declared value even if unused, rechecks history before Complete and rechecks it after verification. Existing output directories cannot be reused.

An already-cancelled call stops before reading command inputs, acquiring a launcher lease, creating output or starting a worker. Registration checks cancellation before publishing Pending. After Pending, the declared-input route preserves its entire literal schedule; the allocated route preserves the journal and blocking claim, including any unresolved derivation. Cancellation cannot permit a retry. Launcher setup time is deducted from the same deadline before the worker starts; setup failures after output creation retain a failure record.

A complete publication requires `completion.json`, the exact root `files.json` inventory and no `failure.json`. Worker/proposed artifacts are intermediate evidence. A failure marker invalidates interrupted publication even if some final-looking files exist. Nothing deletes partial evidence or refunds reservations.

Before publishing, the parent reconstructs the decision and seed-free team sheet from the worker's verified study report and checks the complete proposed artifacts, verification receipt and attempt ledger. A later audit also reconstructs `practical.md` and checks the request version, launch deadline, prior-byte charge, worker request binding and required historical pins. Recomputing file hashes alone cannot make inconsistent publication records pass. The audit reads the saved source definition and study; it does not require the original live definition or content directories to remain available.
